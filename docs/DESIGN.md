## 1. 目标与成功指标

### 1.1 项目目标（D1）

| 优先级 | 目标 |
|---|---|
| 首要 | 自用便利——在碎片时间里可持续地读书 |
| 次要 | 获得一定的开源影响力 |
| 非目标 | 技术创新、收入（收入为 nice-to-have） |

### 1.2 阶段一成功指标（D2）

**连续打卡 21 天不断签。**

唯一验收标准。所有设计以"降低每日摩擦、保证每日闭环可完成"为最高优先级。

### 1.3 派生约束

- 每日时间预算 **10–15 分钟**，含阅读 + 答题 + 打卡全流程
- 21 天 × 12.5 分钟 ≈ **4.4 小时净阅读时间**；SICP 第一章需 15–25 小时，故 21 天窗口内**读不完第一章**（约完成 1/4）
  - 这不影响成功指标（指标是连续打卡而非读完），但影响进度感 → 见 §6.3 进度呈现
- 任何可能让单次 session 超时或失败的环节（网络请求、运行时 LLM 调用），都是对成功指标的直接威胁

## 2. 产品定位

**类比对象不是 Duolingo，而是 Anki + 阅读日历。**

Duolingo 的 streak 依赖损失厌恶（断签清零产生痛感）。D3 决定断签**只记录不惩罚**，动机源因此换成进度可视化与复习闭环的正反馈。后续所有 UI 设计据此——不做惩罚性提示，重做进度呈现。

## 3. 核心循环（D3）

### 3.1 每日 session 流程

```
启动
 ├─ 前情回顾：累计阅读进度的回顾（2026-08 落地实现，见 §3.1.1）
 ├─ 阅读：按当前每日时长目标动态打包若干原子块，一次性全部输出（2026-08 修订，见 §7.4）
 ├─ 答题：新内容理解题(2) → 错题 → 其余到期复习项（超预算则停止）
 ├─ 习题（可选）：今天读过的 block 解锁的原书 Exercise，见 §3.3.1
 └─ 打卡判定
```

回顾 → 阅读 → 答题 → 习题四段之间各插一个"按 Enter 继续"的过渡 + 一条醒目的
分割标题（`Recap` / `Reading` / `Review Questions` / `Exercises (optional)`），
帮用户知道自己在今天流程的哪一段。

### 3.1.1 前情回顾（2026-08 新增）

跟 block 的 `recap_md`（构建期一次性写好、每个 reader 看到的都一样）不同，
这段回顾是**因人而异、每天都在变**的——取决于这个用户具体累计读到哪了。这跟
铁律 2（阅读器绝不调用 LLM/联网）天然冲突：不可能在构建期就把"每个用户每天
具体读到哪"都预先算好。

当前实现（阶段一先做的简化版，见下"未来"）：

- **假设固定的每日阅读时长（12 分钟）来决定回顾的切分粒度**：把 `packSession`
  本身反复套用在整本书上，模拟"如果严格按 12 分钟/天读、一天不落"会在哪些
  block 处产生"一天的终点"——这些终点就是回顾的自然切分单位（`core/recapCheckpoints.ts`
  的 `computeCheckpointBoundaries`）。
- **每个切分终点对应一条回顾**，由人工（Claude）一次性写好、存进内容包
  （`recap_checkpoints` 数组），不是每天现场生成——**阅读器运行时不调用任何
  API，只是查表**，完全符合铁律 2。
- **查表按累计读过的 block 数定位，不按"第几天"**：找"不超过用户实际累计读过
  的 block 数"里最靠后的那条回顾（`findApplicableRecapCheckpoint`）。这样即使
  用户实际节奏跟"12 分钟/天"这个假设完全对不上（调整过目标、超前阅读、断签
  又续上……），回顾依然定位准确——12 分钟这个假设只影响回顾切得多细，不影响
  运行时查找的正确性。
- 第一天（累计读过 0 个 block）没有任何回顾适用，直接跳过这一段。
- 花在回顾上的时间计入当天阅读时长反馈，但不影响 `est_seconds`/block 切分——
  跟习题时间同一条规则。
- 长度目标：≤ 一个"12 分钟标准日"的 25%，而不是当天实际目标的 25%（当天
  实际目标是运行时变量，回顾是构建期写死的，没法动态跟着变）。

**未来（接入真实 API 之后，见项目里记录的 idea 1/idea 3 关系）**：回顾改成
在用户首次开始阅读时设定阅读时长，据此动态切分全书并现场生成回顾文本——
到那时候"阅读器绝不调用 LLM"这条铁律本身需要重新讨论（现场生成必然意味着
阅读器在运行时联网调 API），不是这次阶段一实现要解决的问题。

### 3.2 打卡判定条件

**完成当日分配的阅读内容 AND 完成当日题目。**（2026-08 修订：不再要求阅读时长达标——时长只作为完成后的参考反馈，不作为打卡门槛，理由见下）

- 阅读时长目标由用户设定，**且可随时动态调整**（读不完可调短至舒适为止）
- 打卡完成后展示当天实际阅读耗时；耗时明显少于目标 → 鼓励 + 询问是否明天调高目标；耗时明显多于目标 → 鼓励 + 询问是否明天调低目标；接近目标则只展示耗时，不追问
- 答错时立即显示答案与解析，将该知识点降至 box 0
- "完成"题目只看是否作答过，不看对错——答错会立即扣到 box 0，但不影响今天能不能打卡，否则会变成变相的惩罚机制，违背 D3 的"断签只记录不惩罚"

### 3.2.1 打卡后重新打开（2026-08 新增）

当天已经打过卡、又重新运行 `today` 时，先问用户要做什么：

- **复习今天内容**：原样重放今天读过的 block（按 `block_read` 事件筛出today
  这个打卡日读过的 block id），不产生任何新事件——纯粹重看，不影响阅读进度、
  不重新答题、不触发新的 checkin。
- **超前阅读**：照常打包"目前为止还没读过的下一批内容"并进入正常的
  阅读+答题+打卡流程。因为 `readBlockIds` 是全书累计的（不是按天分桶），
  提前读掉的 block 自然会被后续每一天的打包逻辑跳过——不需要额外的"明天
  起始点 offset"逻辑，这是数据模型本身的性质，不是新写的特殊分支。这可能
  再触发一次同一天的 `checkin` 事件，无害：`checkinDates` 是去重的 Set。

### 3.3 题目分两类

| 类型 | 来源 | 每日数量 | 作用 |
|---|---|---|---|
| 新内容理解题 | 当日读过的原子块所属知识点中抽取 | **固定 2 道** | 保证打卡条件**永远可达成** |
| 到期复习题 | Leitner 调度产出 | 浮动，可能为 0 | 对抗遗忘 |

> 若只有到期复习题，某天到期数为 0 会导致"完成题目"这一打卡条件悬空。

### 3.3.1 原书习题（Exercise，2026-08 新增，第三种、可选做）

原书自己的 Exercise（如 "Exercise 1.9"）单独建模成 `exercises`，跟上面两种
"复习题"是完全不同的东西：

| | 复习题（3.3 表里的两种） | 原书习题（Exercise） |
|---|---|---|
| 是否必做 | 每天必做，是打卡条件的一部分 | **可选**，跳过不影响打卡 |
| 判分 | 离线自动判分（单选题） | **不判分**——开放题，用户自己做，App 不检查对错 |
| 答案 | 有，答错立即显示 | **暂不提供**，只给一条 hint（提示，不是答案） |
| 出现时机 | 每日固定/到期触发 | 读完某个 block 后解锁，用户自己选要不要做 |
| 调度 | 进 Leitner box | 不进任何调度，只记录"碰过"（`attemptedExerciseIds`） |

- 每道原书习题必须标记出来（不能混在正文里当普通阅读内容读过去），也不能
  跟复习题重复——同一段习题内容只能归入 `exercises` 一处，不能既是
  `exercises` 条目又被另造一道 `knowledge_items`/`questions`。
- 习题原文（`prompt_md`）跟 block 的 `content_md` 一样，是按边界索引从原书
  机械切出来的，不是复述（铁律 6 的延伸）；`hint_md` 才是生成器自己写的。
- 用户做习题（包括看 hint）花的时间，**计入当天阅读时长反馈**（3.2 的
  "读少了/读多了"那套逻辑），但**不参与 block 切分的 est_seconds 估算**——
  切分永远只按原文文字量估算，跟用户实际做题要花多久无关，那是用户自己的
  节奏。
- 对应新事件类型 `exercise_attempt`（`exercise_id`/`seconds`/`used_hint`）。

### 3.4 题目优先顺序

`新内容理解题 → 错题 → 其余到期项`

**已知代价**：时间预算固定时，新内容题吃掉多少，复习就少做多少。长期风险是"读得多、记得少"。缓解手段是把新内容题严格锁在 2 道。

### 3.5 断签处理

只记录，不惩罚，连续数照旧累加。必须提供打卡热力图（CLI 与网页版都要有）。

## 4. 内容模型（D4）

### 4.1 原子块（Block）

**内容不能预切成"每日单元"，只能切成原子块，运行时再按当前时长目标动态打包。**

理由：每日时长目标可动态调整（§3.2），预切死的固定日单元在调整后即作废。

规格：
- 每块约 **2–3 分钟**阅读量
- 语义完整，**不跨小节边界**
- 须带**预估阅读时长**（依据字数、公式密度、代码密度估算）

### 4.2 知识点（KnowledgeItem）

- 由 LLM 基于内容理解生成
- 关联一个或多个原子块
- 是**复习调度的最小单位**

### 4.3 内容制品形态（D4c）

**结构化 JSON/Markdown 内容包。**

| 维度 | JSON 包（选中） | 运行时解析 epub | SQLite |
|---|---|---|---|
| 静态站可用性 | `fetch()` 直读，零依赖 | 需 JSZip + XML，每次重跑 | 需 sql.js（wasm ~1MB） |
| Git 友好 | 可 diff、可 review | 原件二进制 | 二进制，全量变更 |
| 版权隔离 | 内容包目录可分离分发 | 最差 | 中等 |
| 阶段三迁移 | 可灌入任何数据库 | 需先转 JSON | 最平滑 |

排除理由：
- **运行时解析 epub**：LLM 切分与出题是构建期昂贵操作，不可能放运行时；知识点与题目仍需另存，该方案退化为"JSON 包 + 多一层解析"
- **SQLite**：数据量级（数百块 + 数百知识点）内存过滤即可；上数据库买不到收益，却付出不可 diff 与 wasm 依赖两个代价

### 4.4 生成/阅读边界（D4d）

**彻底解耦成两个组件，以内容包 schema 为唯一契约。阅读器不得依赖生成器内部结构。**

| 组件 | 运行位置 | 需要 LLM API | 职责 |
|---|---|---|---|
| 生成器 | 本地，构建期，跑一次 | ✅ | 源文件 → 内容包 |
| 阅读器 | CLI + 浏览器，运行期 | ❌ **零网络** | 消费内容包，管理用户状态 |

派生约束：
- 内容包 schema 必须带 `schema_version`，阅读器加载时校验并明确报错
- 阅读器不能调 LLM ⇒ **所有 LLM 产物必须在构建期落盘** ⇒ **题目必须可离线自动判分**
- 阶段三时生成器整体搬到服务端，阅读器几乎不改

### 4.5 内容包物理位置（D7）

```
kuibu/
  packs/public/sicp/        ← 进 git，可被 GitHub Pages 部署
  .gitignore                ← 排除 packs/private/
packs-private/              ← 仓库树之外 或 被 gitignore
```

> ⚠️ **git 陷阱**：`.gitignore` 对**已 tracked 的文件无效**。私有包一旦被 `git add` 过一次，之后加 gitignore 也拦不住。
> 强制顺序：先写 `.gitignore`，再放内容包；禁用 `git add -A`；加 pre-commit hook 检查 staged 文件是否命中 private 路径。

**网页版的第二条分发路径（2026-08 新增）**：`packs/public/` 是"构建期打进
部署产物"，而 `npm run bundle`（`scripts/bundle-pack.ts`）是"构建期打成
单文件、运行时由用户手动导入"——两条路径共用同一份 schema，内容包本身
不因为走哪条路径而改变形状。bundle 产物（`bundles/<book_id>.kuibu.json`）
遵循跟 `packs/private/` 一样的隔离逻辑（.gitignore + pre-commit 双重
拦截，规则先于脚本存在），因为私有书的 bundle 输出同样是受版权保护原文的
派生物。这条路径的意义是让 `packs/private/` 的书能到达用户自己的手机
浏览器，而不必进入构建产物、不必公开分发——运行时解析 epub 仍然是否决的
（见下方否决表/CLAUDE.md），bundle 只是把已经生成好的 JSON 换了个传输方式。

## 5. 复习调度（D5, D9）

### 5.1 算法

**阶段一用固定间隔 Leitner，调度器做成可替换的策略接口。**

```ts
interface Scheduler {
  due(items: KnowledgeItem[], history: Event[], today: Date): KnowledgeItem[];
  onAnswer(itemId: string, correct: boolean, state: ItemState): ItemState;
}
```

理由：21 天窗口内任何间隔 > 21 天的分支都不会执行，Leitner / SM-2 / FSRS 在成功指标下无法区分优劣。重要的是保留替换能力，阶段二积累复习日志后可换 FSRS。

### 5.2 Box 与起步档位（D9）

| Box | 间隔 | 进入条件 |
|---|---|---|
| 0 | 1 天 | 答错 |
| 1 | 3 天 | 答对（首次） |
| 2 | 7 天 | **当日读过但未被抽中出题**（起步位） |
| 3 | 15 天 | 连续答对 |
| 4 | 30 天 | 连续答对 |

**所有当日读过的知识点全部入队**，不存在"读了却不追踪"的知识点。未出题的从 box 2 起步。

副作用（正面）：当日 8 个知识点中 2 个在 1–3 天后到期、6 个在 7 天后到期，**复习负载自动错峰**，避免同批同时到期。

⚠️ 张力：未出题的知识点是**未经验证**的，给更长间隔等于假设已掌握——这是 §5.3 拒绝的"虚假掌握"失效模式的弱化版。可接受，但起步位不应高于 box 2。

### 5.3 债务控制

- 按时间预算截断，**错题优先**
- 超预算的到期项当天不做，**视同未到期，明天继续排队**（不视同答对）
  - 反例：若视同答对则间隔照常延长，产生**虚假掌握**——从未答过却被判定已掌握
- ⚠️ 顺延语义会导致积压。观测手段（待复习积压数）**已排入阶段二**，阶段一无预警机制

### 5.4 错题复习

**只重复原题**，不预生成变体题（保持内容包体积最小）。

**选项顺序必须在运行时随机打乱**——否则重复三五次后记住的是"答案在 B 位"而非知识点。这是 leech 最常见的形式，shuffle 一行代码消掉大半。

⚠️ 剩余 leech 风险（记住题干字面而非知识点）的标准补丁"连续答错 N 次挂起并提示回读原文"**已排入阶段二**。

## 6. 用户状态与同步

### 6.1 事件日志（append-only）

**用户状态存为 append-only JSONL 事件日志，而非可覆盖的状态快照。**

驱动需求：异常退出时保证阅读记录不丢失（v0.1 Must）。

```jsonl
{"id":"...","ts":"...","type":"session_start","book_id":"sicp","target_seconds":720}
{"id":"...","ts":"...","type":"block_read","block_id":"b0001","seconds":148}
{"id":"...","ts":"...","type":"answer","question_id":"q0001","correct":false}
{"id":"...","ts":"...","type":"checkin","date":"2026-08-01"}
{"id":"...","ts":"...","type":"settings_change","key":"daily_target_seconds","value":600}
```

收益：
- **崩溃安全**：每个动作追加一行并落盘，崩溃最多丢最后一行
- **多端同步几乎免费**：按 `(ts, id)` 去重排序即可合并两端日志。快照式状态文件合并时会产生"哪边赢"的冲突，事件日志天然可合并
- **可视化直接来自聚合**：热力图 = 对 `checkin` 事件按日期聚合

代价：需要 reducer 将日志折叠为当前状态；日志增长后需快照压缩（阶段二）。

### 6.2 存储介质

| 环境 | 介质 |
|---|---|
| CLI | 本地 JSONL 文件 |
| 网页版（阶段二） | IndexedDB |
| 导入导出 | 同一份 JSONL，两端通用 |

### 6.3 进度呈现（D9）

**小节进度与整章百分比同时显示**，例如：`1.1.3 已读完 · 第一章 23%`。

小节粒度提供可达成的完成感（对抗 §1.3 的"21 天读不完第一章"）；章节百分比提供全局定位。

## 7. 组件架构与技术选型（D6）

### 7.1 分包

```
pack-gen/     Python      构建期工具，调 LLM，产出内容包
core/         TypeScript  纯逻辑，零 IO —— session 打包器、调度器、reducer、schema 校验
cli/          TypeScript  core + 文件 IO + pager + 终端 UI
web/          TypeScript  core + IndexedDB + DOM（阶段二）
schema/       JSON Schema 单一真相源
```

**`core` 必须是纯函数库、零 IO**——这是 CLI 与网页版真正共用逻辑的前提。文件读写、网络、终端输出、计时器全部留在 `cli` / `web` 层。

计时接口由 `core` 定义、两端各自实现：

```ts
interface BlockTimer {
  start(blockId: string): void;
  stop(blockId: string): number; // 返回秒数
}
```

- CLI 实现（2026-08 修订）：今天全部 block 一次性输出到"用户按 Enter 表示读完"
  之间的总时长，再按各 block 的 `est_seconds` 占比分摊——不再是逐 block 进出
  pager 计时（原因见 §7.4）
- Web 实现：block 可见时计时

### 7.2 语言选择理由

- **生成器用 Python**：只在本地跑一次、永不进浏览器；epub/HTML 解析与 LLM SDK 生态最成熟；上手最快
- **阅读器用 TypeScript**：需 CLI 与浏览器两端共用，TS 是唯一能做到零重写的选择
- D4d 的解耦解开了语言绑定，两组件用不同语言不是妥协，而是解耦的正当红利

### 7.3 Schema 契约的双语言校验

JSON Schema 文件作为唯一定义，两侧各自生成校验器：

| 侧 | 工具 |
|---|---|
| Python（生成器） | pydantic |
| TypeScript（阅读器） | zod 或 ajv |

否则字段定义会在两个语言间漂移。

### 7.4 CLI 交互形态（D7，2026-08 修订：去掉 pager）

**单命令一次性流程 + 直接 stdout 输出正文。** 二进制名 `kuibu`，日常入口 `kuibu today`。

- 单命令模式下**断点续读天然成立**——退出即断点，无需额外设计
- 排除 TUI 的理由：开发成本高，且 TUI 代码阶段二一行都用不上；叠加 TypeScript 学习成本（R6），是明显的时间陷阱

**原方案是逐 block 经系统 pager（`less`）呈现，2026-08 改成把当天全部 block
一次性打印出来，理由（用户直接反馈）**：pager 的"一块读完、退出 pager、再进
下一块"这套逐块暂停，在实际使用中是多余的操作和眼球转动，对阅读体验没有
实质帮助；终端本身就有滚动缓冲区，不需要额外套一层 pager 才能回看。原来
认为 pager 提供的"干净计时锚点"（§7.1）现在改成：全部内容一次性展示 → 用户
按 Enter 表示读完 → 按各 block 的 `est_seconds` 占比把这段总时长分摊回每个
block——计时粒度从"进出 pager"变成"分摊估算"，代价是单个 block 的实际耗时
不再精确，换来的是显著减少的交互摩擦。原来"pager 不可用环境需要降级"这条
顾虑也随之消失——不再依赖任何外部程序。

阅读 → 答题 → 习题三个环节各自用一条醒目的分割标题隔开（见 §3.1）。章节号
最初放在标题左侧、按层级拼接（如 `Chapter 1 › 1.1 › 1.1.3`），后来（2026-08，
用户实测反馈"和真书很不一样，每个 block 都重复一遍完整路径"）改成跟真书
排版一致的**增量式标题**：只在章/节/小节号相对上一个 block 变化的那一级
开始打印从那一级往下的标题，同一小节内连续的 block 之间完全不重复标题；
章一级固定带 `Chapter N` 前缀，其余层级只写编号本身，靠缩进（而不是重复的
`Chapter 1 › ...` 前缀）表达层级关系——实现见 `cli/renderBlocks.ts` 的
`computeHeaderLines`，中间层级的标题文字取自 `pack.section_headings`（同一份
`SectionHeading` 数据，见 §9 与 `status` 的目录展示）。

如果今天的阅读是接着某天断在小节中间的位置继续（不是正好从小节边界开始），
第一个 block 的标题下面会补一行 `...`，代表"这里之前还读过一部分，不重复
打印"——不需要把已读过的正文再显示一遍。正文每一行也会加统一缩进（比这个
block 自己的小节标题再深一级，`cli/renderBlocks.ts` 的 `indentContent`），
让正文在视觉上"挂在"标题下面。（最初曾以"避免跟代码块缩进混在一起"为由
跳过这一步，用户实测后反馈仍然希望做，2026-08 补回。）

`content_md` 里一个段落是不含换行符的一整行长文本——只给这一整行开头加
前缀并不够：这行长到超过屏幕宽度时，终端自动折行的续接部分并不知道这行
本身带了缩进，续接处会贴回屏幕左边（"首行缩进、后面顶头"，2026-08 用户
实测发现）。所以 `indentContent` 不依赖终端的自动折行，而是自己按
`width - 缩进长度` 手动断词换行（贪心算法 `wordWrap`），断出来的每一行
单独加前缀；`width` 优先取 `process.stdout.columns`（真实终端宽度），
拿不到时（比如输出被重定向）退回 80。Scheme 代码块内部**不**参与断行——
重新折行会打乱代码本身的换行/缩进——只整体加前缀跟着正文一起右移。

代码块的 ` ```scheme ` / ` ``` ` 围栏标记本身**不打印**（2026-08 用户反馈：
纯文本终端不解析 Markdown，这两行围栏在 Windows 终端里既不高亮也不成框，
杵在那里纯属多余）。换成一行纯文本提示：开头围栏换成 `Code (scheme):`（没有
语言标注就是 `Code:`），紧跟一条 `---` 边界线，代码结束后再来一条同宽度的
`---` 收尾。选择纯文本而不是 Unicode 画框或 ANSI 颜色，是为了不用考虑
"Windows 终端到底支不支持"这类兼容性问题，任何能显示 ASCII 的终端都能正确
显示。边界线的宽度取代码块里最长一行的长度，不拉到屏幕宽度——拉满屏幕会
跟"分页/分节"的横线混淆，用户明确反馈过（`indentContent` 里先把代码块的
所有行缓冲下来，闭合围栏那一刻才知道最长行有多长，再一次性吐出
标签+边界+代码+边界）。

`Recap` 环节的头部也补了一份跟 `status` 一样的目录（`renderTableOfContents`
+ `→ ... (you are here today)`），让用户在看回顾文字之前先看到自己当前在
全书里的位置，不需要额外去跑一次 `status`。

## 8. 生成器规格（D8）

### 8.1 调用粒度

> ⚠️ **"单次调用产出全部"在整本书粒度上不可行。** SICP 第一章约四万词，切成 2–3 分钟的块约 150–200 块；一次输出全部块 + 知识点 + 题目将达几百 KB，远超单次输出上限，且截断后无重试粒度。

保留原意图（三件事一起做、上下文一致、不搞三段 pipeline）的可行方案是**把"单次"的粒度降到一个小节**：

```
机械切分（脚本，无 LLM）：第一章 → 小节 1.1.1 / 1.1.2 / ...
  └─ 每个小节一次 LLM 调用 → 该节的原子块 + 知识点 + 题目
```

- 一次调用内三件事仍共享上下文
- 失败只需重跑该节
- 中间产物落盘，支持增量恢复与幂等重跑

### 8.2 LLM 不复述原文

**LLM 只输出块的边界索引**（段落序号或字符偏移）+ 元数据（`est_seconds`、`recap_md`），原文由脚本按边界切割。

两个理由：
1. 输出量从几百 KB 降到几 KB
2. **防止 SICP 的 Scheme 代码被 LLM 悄悄改写**——在技术书里这是灾难性的

### 8.3 输入适配器

```
SourceAdapter: 源文件 → 归一化的带结构纯文本（章 / 节 / 段落 / 代码块）
  ├─ TexinfoHtmlAdapter   SICP
  └─ EpubAdapter          小说类书籍（阶段二，2026-08 开始实现，详细设计见 §14）
```

下游流程与源格式完全解耦——`EpubAdapter` 不要求 `slice_section.py`/`build_all_sections.py` 改一行代码，是这条解耦的实测验证。

### 8.4 出题规格

题型限定为**选择题**（D7）：概念理解型文字题、代码片段判断题皆可，但一律给出选项，**不要求用户输入文本**。

**干扰项质量是生成器的核心指标。** 选择题可靠排除法蒙对，唯一防线是干扰项。生成器 prompt 必须明确要求：

> 每个干扰项必须是学习者的**常见误解**，不能是明显荒谬或格式明显不同的选项。

否则 LLM 默认产出"一个正确答案 + 三个凑数选项"，题目失去检验价值。

## 9. 内容包 Schema 草案

```
pack/
  manifest.json     schema_version, book_id, title, author, license,
                    source, generated_at, generator_version
  blocks.json
  items.json
  questions.json
  exercises.json
```

**Block**
```json
{
  "id": "b0001",
  "seq": 1,
  "section_path": ["1", "1.1", "1.1.1"],
  "section_title": "Expressions",
  "content_md": "...",
  "est_seconds": 150,
  "recap_md": "一句话摘要"
}
```

> `recap_md` 放在 block 级而非 session 级：session 是运行时动态打包的，其摘要无法在构建期预生成。回顾功能通过拼接"昨天读过的 blocks 的摘要"实现。

**KnowledgeItem**
```json
{
  "id": "k0001",
  "block_ids": ["b0001", "b0002"],
  "statement": "知识点陈述",
  "question_ids": ["q0001"]
}
```

**Question**
```json
{
  "id": "q0001",
  "item_id": "k0001",
  "type": "single_choice",
  "prompt": "...",
  "options": ["...", "...", "...", "..."],
  "answer_index": 2,
  "explanation": "..."
}
```

> `options` 在**运行时随机打乱**后呈现（§5.4）。故存储用 `answer_index` 而非固定字母。

**Exercise**（2026-08 新增，见 §3.3.1）
```json
{
  "id": "x0001",
  "block_id": "b0001",
  "number": "1.9",
  "prompt_md": "...",
  "hint_md": "提示，不是答案"
}
```

> `block_id` 决定这道习题何时解锁（读完这个 block 之后）；`prompt_md` 跟
> `Block.content_md` 一样是从原文机械切出来的，`hint_md` 才是生成器自己写的。

**RecapCheckpoint**（2026-08 新增，见 §3.1.1）
```json
{
  "id": "r0001",
  "through_block_count": 20,
  "recap_md": "..."
}
```

> `through_block_count` 是累计 block 数，不是天数——运行时找"不超过用户实际
> 累计读过的 block 数"里最靠后的一条，不依赖任何每日阅读时长假设。

**SectionHeading**（2026-08 新增）
```json
{
  "path": ["1", "1.1"],
  "title": "The Elements of Programming"
}
```

> 章/节这一级（不是 block 的叶子小节）的标题，纯机械从原文标题标签提取
> （`TexinfoHtmlAdapter.extract_section_headings`），不需要人工/LLM 参与。
> `kuibu status` 的目录用它在叶子小节之间插入"1"/"1.1"/"1.2"/"1.3" 这几级
> 标题行，配合缩进呈现出正确的层级关系，而不是一串平铺的叶子小节。

## 12. "一天"的边界（D10）

**偏移自然日。** 打卡日 = 以本地时间凌晨 4:00 为界划分的自然日；凌晨 1 点读书计入前一天。

```ts
function checkinDate(ts: Date, offsetHours = 4): string {
  const shifted = new Date(ts.getTime() - offsetHours * 3600_000);
  return shifted.toISOString().slice(0, 10); // 需按本地时区实现
}
```

- 偏移小时数写入配置，默认 4
- 排除本地时区自然日：23:50 与次日 00:10 各读一次会被算作连续两天，实际中间跳了近 24 小时
- 排除滚动窗口（距上次打卡 36 小时内即算连续）：最不易断，但"连续天数"会失去日历意义
- ⚠️ 事件日志中 `checkin` 事件必须存**已换算的打卡日**（`date` 字段），不能只存 `ts` 后期再算——否则改配置会静默重写历史 streak

## 14. 阶段二设计：多本书与 EpubAdapter（2026-08 新增）

### 14.1 范围与动机

用户决定不必等 SICP 的"连续打卡 21 天"（阶段一唯一验收指标）先跑完，两条线并行：
**SICP 打卡继续是阶段一验收标准本身**，`EpubAdapter`/多本书支持是阶段二的第一块拼图，
独立推进，互不阻塞、互不干扰——具体如何互不干扰见 §14.4/14.5。

顺序（用户拍板，先易后难）：

1. **The Great Gatsby**（英文，公有领域）—— 验证 `EpubAdapter` 解析链路本身
2. **一本中文小说**（书目、版权状态待定）—— 验证生成内容随源书语言切换这条既有约定
   （见项目记忆 `feedback_language_rules`）在小说场景下依然成立
3. **用户自己的 epub**（可能非公版）—— 走私有包路径，见 §14.6

小说**没有 Exercise**：§3.3.1 的原书习题模型是 SICP 特有的，小说没有对应物，
`exercises` 直接是空数组——不需要任何 schema/代码改动（8 个 SICP 小节已经这么用过）。
内容生成方式跟 SICP 完全一致：人工代 LLM 手写（尚未接入真实 API），产出遵守铁律 6
（不复述原文，只给边界索引）。

### 14.2 内容模型的差异

- SICP 的 `section_path` 是三级（章/节/小节），小说只有"章"一级，形如 `["6"]`；
  `SectionHeading` 依然可用，只是层级浅得多——schema 本身不用改（`section_path` 只要求
  `minItems: 1`，没有固定深度约束）。
- 没有代码块 → `cli/renderBlocks.ts` 的 `indentContent`/`Code (scheme):` 那套渲染逻辑
  天然不会被触发，不需要为小说改一行阅读器代码。

### 14.3 EpubAdapter 技术方案

基于实际下载并解压 Project Gutenberg 官方 epub（ebook #64317）验证，不是拍脑袋设计：

- epub 是标准 zip，`META-INF/container.xml` 指向 `content.opf`（OPF manifest + spine
  决定阅读顺序）。
- **实测发现 Gatsby 的 epub 把全书内容摊在 spine 里的 3 个 xhtml 文件里，不是像 SICP 源码
  那样每个小节一个文件**：
  - `*-h-0.htm.xhtml`：Gutenberg 页眉样板 + 标题页 + 目录 + 第 I–V 章
  - `*-h-1.htm.xhtml`：第 VI–IX 章
  - `*-h-2.htm.xhtml`：纯 Gutenberg 版权/许可样板（整篇丢弃）
- 每一章是一个 `<div id="chapter-N"><h2>罗马数字</h2><p>...</p>...<hr/>...</div>` 块；
  `<hr/>` 是章内的场景分隔符（不是新章节），正文段落是纯 `<p>`，强调用 `<i>`。
- `EpubAdapter.parse()` 策略：
  1. 按 spine 顺序遍历 xhtml 文件；
  2. 一个文件里如果找不到任何 `<div id="chapter-*">`，整篇跳过（页眉/页脚样板不需要
     逐段落甄别，直接按"有没有章节 div"这个粗粒度信号过滤）；
  3. 每个 `chapter-N` div 内，`<h2>` 文本作为该章标题（罗马数字换算成阿拉伯数字存进
     `section_path`，标题原文存进 `SectionHeading`）；
  4. `<p>` 顺序收集成段落列表；`<hr/>` 记为场景分隔标记，暂定不强制作为 block 边界
     （场景分隔不一定卡在 2–3 分钟的整数倍上，留给切块脚本按字数决定）；
  5. 输出跟 `TexinfoHtmlAdapter.parse()` 完全一样的 `Subsection` 结构，下游
     `slice_section.py`/`build_all_sections.py` 不需要改一行代码。
- Gatsby 没有 SICP 那种"章引言"结构，`_parse_chapter_intro` 分支这里用不上——每章直接从
  `<h2>` 开始。

### 14.4 多本书事件日志隔离

**现状缺口**：`block_read`/`answer`/`checkin` 事件都不带 `book_id`（只有 `session_start`
带），加载时对"当前 pack 是否匹配当前日志"也没有任何校验——单本书时这个缺口不会暴露，
多本书并存后必须补上。否则一次手滑（`--pack` 换了、`--log` 忘了换）就会让两本书的 block id
（各自都从 `b0001` 起步）在同一份日志里打架，污染 SICP 那份真实的 21 天记录。

方案（已跟用户确认，用哪种隔离方式是明确问过的决策点，不是我自己选的）：

- **不改事件 schema**（不给每种事件都加 `book_id`——那是更大的改动，还会碰到已经产生
  真实数据的 `.kuibu-events.jsonl`），改用**每本书一个独立日志文件**，复用已有的 `--log`
  CLI 参数机制。
- `--log` 的默认值不再硬编码 `.kuibu-events.jsonl`，改成按 `--pack` 目录名推导：
  `packs/public/sicp` 继续默认 `.kuibu-events.jsonl`（老用户默认路径不能变），
  `packs/public/gatsby` 默认 `.kuibu-events-gatsby.jsonl`，以此类推；用户仍可用 `--log`
  显式覆盖。
- **加载时校验**：日志非空且已有 `session_start` 事件时，若其 `book_id` 跟当前
  `pack.manifest.book_id` 不一致，直接拒绝运行并报错，而不是静默把两本书的状态折算成
  一个 `ReducerState`。
- `.gitignore` 需要从精确匹配 `.kuibu-events.jsonl` 改成通配 `.kuibu-events*.jsonl`，
  否则新书的默认日志文件不会被自动忽略。

### 14.5 CLI 默认行为不变

`kuibu today`/`kuibu status` 不传 `--pack` 时依然默认 `packs/public/sicp`——SICP 是且仍是
默认阅读对象，新书必须显式 `--pack packs/public/gatsby` 才会切换。**唯一成功指标**
（连续打卡 21 天）在这次改动后依然只认 SICP 那份日志；新书的打卡/streak 是独立的、
次要的功能验证，不计入也不会稀释这个指标。

### 14.7 推进节奏

不追求一次性做完整本书：先用 Gatsby 前几章验证"epub 解析 → 机械切块 → 手工出题/recap
→ `packs/public/gatsby` 组装 → `kuibu today --pack packs/public/gatsby` 完整走一遍，
确认不影响 SICP 现有体验/命令行为"，再决定是否铺开全书——跟当年 SICP 先做 1.1 一节
再铺开是同一个套路（见 `docs/JOURNAL.md` 2026-07-31 M3 条目）。西游记同理：先做前
10 回让用户验收，通过再铺开剩余 90 回，见 §14.8。

### 14.8 第二个 SourceAdapter：`GutenbergTxtAdapter`（2026-08 新增）

`EpubAdapter` 是照着 Gatsby 那份 epub 的结构设计的——"ebookmaker 从 HTML 源转换"
这一种 Gutenberg 工具链产物，`<div id="chapter-N">` 是可靠的章节容器。西游记的
Gutenberg 版本（ebook #23962）是**从纯文本 `.txt` 源转换**的，结构完全不同，
`EpubAdapter` 直接套用会失败，实测验证后新写了 `GutenbergTxtAdapter`：

- **没有任何容器元素**：全书正文就是 spine 文件里一串平铺的兄弟 `<p>`（外加
  `<br/>`），章节靠正文自己的标题行识别，不是靠 `<div>`——构造函数接受一个
  "这段文本是不是章节标题"的正则，不是写死在 adapter 里。
- **样板起止标记是裸 `<span>`，不在任何 `<p>` 里**：`*** START OF THE PROJECT
  GUTENBERG EBOOK ... ***` / `*** END OF ... ***` 直接躺在 body 下面，不像 Gatsby
  那样可以靠"文件里有没有 chapter div"这种标签结构判断。第一版实现在 `<p>` 标签
  内搜索这两个标记文本，一个都没找到（因为压根不在 `<p>` 里）——最终改成在
  **原始字符串层面**用子串查找定位起止位置，裁剪掉样板部分后再交给 BeautifulSoup
  解析剩下的内容，不依赖标记具体被哪个标签包着。
- **章节数字不可信，只信标题出现的顺序**：这版西游记的回目数字写法本身不统一——
  "第一回".."第九回"用标准数字，往后大部分改成逐位读数（"第一二回"表示十二），
  但也有例外用回标准复合数字（"第八十七回"），十位数为零时甚至用"○"（全角圆圈，
  不是"零"字，也不是阿拉伯数字 0）代替。与其解析这堆不一致的写法，adapter 不
  尝试理解数字本身的含义，只按"遇到匹配正则的标题行"的实际顺序自己编号
  （`chapter_num += 1`），原文标题字符串原样保留在 `section_title` 里给读者看。
  实测验证：这个策略找到了全部 100 回，顺序正确。
- **比 Gatsby 更简单**：没有 `<blockquote>`/`<table>`，诗词是穿插在叙述段落里的
  （同一个 `<p>` 用 `<br/>` 分行），不是独立的引文块，`_paragraphs_from_element`
  那套按标签类型分发的逻辑在这里用不上，`GutenbergTxtAdapter.parse()` 直接对每个
  `<p>` 调 `html_text.render_inline`/`clean_text` 就够了。

两个 adapter 都要用到的 zip+OPF 解析和 `<br/>` 保留换行的内联渲染，抽成了
`epub_zip.py`/`html_text.py` 两个共用模块——第二个 adapter 出现后，这是真实的
代码重复，不是投机式的提前抽象。
