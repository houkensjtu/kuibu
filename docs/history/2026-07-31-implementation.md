## 1. 起点：从设计文档到分步实现计划

产品定义完成、`docs/DESIGN.md`/`docs/MILESTONES.md`/`CLAUDE.md` 都已就位之后，Qian 先让
Claude 理解仓库的开发动机和前期设计考虑，然后明确要求：**把 M0-M4 按功能切分成更细的步骤，
每一步都对应一个具体、有意义的功能点，做完能让他自己跑一条命令验证效果**——而不是一次性做完
再看结果。

Claude 据此把 M0-M2 拆成了 20 步（M3/M4 本身粒度已经够细，小幅拆分），产出一份 25 步计划
（存在 `radiant-squishing-avalanche.md`），Qian 确认后开始执行。

## 2. 执行方式的标准约定

做完前两步后，Qian 提了两条会一直生效的约定：

1. **commit 身份**：用 Claude 的身份提交，除非 Qian 自己写了代码才用他的名义。
2. **自动执行**：后续任务直接自动做、自动 commit，只有需要人工输入内容或做决策时才停下来
   问；push 永远等 Qian 明确要求才做。

这两条此后贯穿了整个实现过程——25 步计划里的大多数步骤都是这样自动跑完、自动 commit，只在
真正需要 Qian 拍板的地方（比如 LLM provider 选型、M3.23 的范围）停下来问。

## 3. M0-M2：闭环先跑通，一步步验证

工具选型（`tsx`/`commander`/`vitest`/`ajv`/`datamodel-code-generator`）确定后，M0（schema +
双侧校验）、M1（`core/` 纯逻辑六件套）、M2（CLI 完整闭环：读→答→打卡→热力图→进度→
可调目标→导入导出）依次落地，每步都有 vitest/pytest + 一个能亲眼看到效果的 demo 脚本或
CLI 调用。中途 Qian 用 winget 装好了本地一直没有的 Node.js/Python 环境。

M2 做完后 Qian 说"等到 M2 再弄，把目前为止的进度做成一个 commit 让我 review，可以了就 push
到 github"——第一次 push 发生在这里。

## 4. M3：要不要接真实 LLM API

M3（生成器）开始时，Qian 一度打算配 API key（先选 Anthropic，又问"我能否用 openai 的"，切换
了依赖），但最终在 M3.22（单小节 LLM 调用）这一步明确改变主意：**先跳过接 API，由 Claude 在
Claude Code 内部直接扮演"LLM"这个角色，手工产出同样规格的内容，以后再回来接真正的 API**。
这个决定此后被反复确认、贯穿了整个内容生成过程（包括最后补完 1.2/1.3 时依然遵守）。

M3.23（全章流水线范围）上，Qian 选择"只搭流水线机制，不再手工写内容"——把机制和内容生产
分开推进。

## 5. 上线后的第一轮用户反馈

M4 上线第一版内容包（当时只有 1.1 的 8 节）后，Qian 用真实环境试用，带回三类反馈，Claude
逐一修复（细节见 JOURNAL.md）：

- 界面和题目语言：CLI 应该是英文，但题目内容要跟随书本身的语言。
- 阅读目标：为什么没问就自己定了默认值。
- 内容缺失：SICP 第一章的引言部分（Locke 引语、"Programming in Lisp"）整段没有——这条反馈
  牵出了两个独立的内容管线 bug（章节引言文件从未被解析、`<blockquote>` 被丢弃）。

同一晚，Qian 报告了一个更严重的问题：**读完第一天内容、刚进入答题阶段，程序在没有任何输入
的情况下就直接退出了**。Claude 排查后发现这是 `readline.Interface.question()` 连续调用两次
导致的真实 bug（`tsx` 和纯 node 下都复现），**主动更正了自己在 M2.16 阶段的一次误诊**（当时
以为是 tsx 特有、跟之前调用过 spawnSync 有关，其实完全无关）。修复后 Qian 又问了"现在应该
怎么测试试用？试用以后如何清空阅读记录？"——这类问题后来直接写进了 README。

## 6. 打卡逻辑的一次重新设计

Qian 提出：打卡不应该卡在"读够指定时长"上，而应该是"读完分配的内容 + 做完题目就算数"；时长
只在完成后作为参考反馈——读少了给鼓励并问要不要明天调多，读多了同样给鼓励并问要不要调少。
这是对 `docs/DESIGN.md` §3.2 原有判定条件的一次实质修订，Claude 同步更新了核心逻辑
（`core/checkinJudgment.ts`）、CLI 提示文案和设计文档本身。

紧接着 Qian 又问了两个体验问题：**现在能不能直接用 `kuibu` 命令**（答案是还不能，需要
`npm link`，日常先用 `npm run dev --`）、**能不能不用每次都打 `--pack`**（改成默认指向
`packs/public/sicp`，因为目前只有这一本书）。同一批还加了 `kuibu status` 命令，用来回应
"有没有办法只看打卡状态、不用整个走一遍今天的 session"这个需求。

## 7. 补完内容 + README（M4 收尾）

Qian 要求把剩下的 M4 任务做完，同时重申了一条已经确认过的约束：**文本解析/内容生成部分继续
沿用之前的做法——Claude 自己手工代替 LLM，不接入真实 API**。因为剩下 10 个小节（1.2、1.3）
彼此独立、规格已经写清楚，Claude 这次没有沿用之前的串行手写方式，而是**为每个小节各起一个
subagent 并行生产**——这仍然符合"人不接 API 手工产出"的约束，只是把执行方式从串行改成了
并行。合并、校验、组装进 `packs/public/sicp/` 后，Chapter 1 第一次有了完整内容（137 blocks /
76 items / 80 questions）。随后补了 README，把日常使用方式、命令一览、如何在不碰真实打卡
记录的前提下试用都写清楚。

这一步过程中发现：**Qian 已经在用真实的 `.kuibu-events.jsonl` 开始了自己的 21 天打卡**——
从这之后，所有验证测试都必须显式指定 `--log` 到临时路径，绝不能碰默认的事件日志文件，这个
边界后续被严格遵守。

Qian 确认后说"push it for today. I will come back and review tomorrow"——push 到这里为止。

## 8. 打卡后重开的体验设计

Qian 提出：打卡完成后如果用户再次打开 kuibu，应该给一个选择——复习今天读过的内容（原样重
放），或者超前阅读（把下一批内容提前读掉并做题，且这部分内容不该在明天再重复出现）。Claude
分析后发现"明天起始点自动 offset"这件事本来就是现有数据模型（`readBlockIds` 全书累计、不
按天分桶）的自然结果，不需要额外实现；真正需要新写的只是"复习"这条路径需要的按天过滤逻辑
（`blockIdsReadOnDate`）和一个选择提示。
